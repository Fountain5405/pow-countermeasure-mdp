## 1. MRL #146 "Share or Perish" (tevador; opened 2025-09-25, last update 2026-10-20, still open, 20 comments)
URL: https://github.com/monero-project/research-lab/issues/146

### Current rule (body as of 2026-10-20; quoted)
- Parameters (Table 1): `w` workshare ratio = 16; `d` network propagation delay = 5; `k` partition recovery = 3.
- "SoP introduces an additional work object called "workshare", which is defined as a distinct PoW header that meets at least `1/w` of the current block difficulty and has the same `prev_id` value as the containing block." "On average, a block will contain `w-1` workshares." Share = 42-43 B (timestamp, nonce, tx_tree_hash, num_transactions); in tx_extra ~170 MB/yr, or a commitment plus separate P2P message. "Blocks without the extra data are still valid and count as having 0 workshares."
- Uniqueness (2.2): "SoP additionally requires miners to set the `minor_version` block header field to be equal to `major_version` plus the number of workshares included in the block. Workshares included in the block must have sequential values of `minor_version` starting from `block.major_version` and ending with `block.minor_version-1`. If more than 200 workshares are produced for a block, only the first 200 are included". "reduces the frequency of long reorgs an attacker can achieve by up to 2 orders of magnitude." Violating blocks "are still valid and count as having 0 workshares."
- Pool (2.3): shares with `prev_id` = tip and sequential `minor_version` are relayed. "Nodes also accept (but do not relay) "alternate workshares" that build on the chain tip of a known alternate chain ... as long as the fork point of the alternate chain is fewer than `10*w` blocks deep."
- Subjective state (3): h0 = height at sync completion; per-node first-seen times for blocks and shares at h > h0; "reference timestamp for height h" is recorded the first time a block of that height is appended to the main chain and "never changed, even if the node later switches chains"; `ref_seen(x)` falls back to `block_seen(x)`. State is not persisted (reset on restart).
- Scores (Table 3): nakamoto = diff(x.height) per block, 0 per share. sop_objective = diff/w per block, diff/w per share in block AND per share in pool. sop_subjective = l_b(x)*diff/w per block; l_b(x)*l_w(x,y)*diff(y.height)/w per in-block share; 0 for pool shares. "Workshares in the workshare pool that extend the chain tip are counted only under the `sop_objective` function."
- Lateness: l_b(x)=0 "if block_seen(x) - ref_seen(x) > d", else 1. l_w(x,y)=0 "if ref_seen(x) - share_seen(y) <= d", else 1. "a share is considered to be late if it's not seen more than `d` seconds before the reference block of the same height."
- Fork choice (5): h_f fork height, h_max highest height, n_max = max work objects above h_f+1 (block at h_f+1 and pool shares not counted). Iterate: "1. ... If h0 < h_f and h_max - h_f < 10*w and n_max < (k-1)*w, select sop_subjective. ElseIf h_max - h_f < 10*w, select sop_objective. Else select nakamoto. 2. Score all chains ... 3. If all chains received the same score, return C. 4. Remove the lowest scoring chain ... 5. If only one chain remains, return C. 6. Recalculate ... go back to step 1." Ties: random among equal chains (5.1). Under nakamoto shares can be ignored for blocks more than 160 below tip.
- Security claims (6): alpha = 1/3, w=16, d=5, k=3. Dilemma: share must be seen >= 6 s before reference block; withheld block must arrive <= 5 s after honest one. "attacker can mine at least 1 private block and 32 other work objects ... the lateness penalties don't apply. ... about once per 1.5 days ... on average a 3-block reorg" (Nakamoto: once per hour). "10+ ... about 1 such reorg per 2 years" (Nakamoto: several per day). Partition recovery "on average after 3 blocks".
- Appendix simulator (MIT): HONEST_HR=6, ATTACK_HR=3 (alpha 1/3), UNIQUE_SHARES=True, UNCLE_BLOCKS=False, COUNT_TIP_SHARES=True, W=16, K=3, STUBBORNNESS=10, GAMMA=0.5, MIN_REORG_DEPTH=10, 200-share cap. "pessimistically assumes the attacker's hashrate is not included in the difficulty calculation": BLOCK_DIFF = 6*120 = 720 hashes, so with 9 H/s a block arrives every 80 s, not 120 s. Attacker keeps mining while honest_work - attack_work <= STUBBORNNESS; success iff score diff < 0 (or tie with prob 1-GAMMA... `random() > GAMMA` fails the tie). Earlier file: github.com/tevador/scratchpad/blob/master/share-or-perish/blockhain-sim.py (comment 2025-12-06).

### Relevance to pcmdp
Already reflected (from docstrings): w=16, K=48=k*w, window "no reveal before 32 objects past a branch's first block" (= 1 block + (k-1)*w), 2026-10-20 rule with honest pending tip shares counted (`x - pa > 0` with ph on the honest side), 11+ depth as the disruption threshold (10-block lock), attacker/honest object walk with 1/w time per object.
Differs or missing, concretely:
1. No lateness/d at all. The race model abstracts l_b, l_w; delay enters only via gamma or not at all. albinjm's results show d and delay dominate: 1 s -> 4.5x, 3 s -> 81x tevador's 10+ frequency. The 0.5 s share delay by tevador vs 3 s by albinjm brackets the realistic range.
2. Own-pending: rule text counts valid pool shares that extend a chain's tip (incl. a revealed attacker's); pcmdp/monerosim default `--own-pending ignore` (from 12-daemon sims), the `count` reading is the text's. Report both; flag as an implementation-vs-text gap.
3. Ties: text 5.1 is random selection; sop_mdp uses "no ties". tevador's sim uses GAMMA=0.5.
4. Uniqueness rule (shares lost to `minor_version` collisions, 15-16% at 3 s, ~0 at zero delay; attacker can still merge honest shares in its first block but not all): not modelled as a loss. Needed for any delay-aware model.
5. Fork choice also has nakamoto beyond 10*w=160 blocks and alt-share acceptance within 10*w; irrelevant at 11+ depth but matters for deep-partition recovery.
6. Subjective h0 term (fresh node resets) not modelled.
7. Tevador's sim clock is 80 s per block at alpha 1/3 (attacker hash excluded from difficulty), albinjm's "per 3 y = 0.0845 per 100k" confirms. pcmdp times are in block intervals; convert before comparing.
8. Comparison gap to chase: tevador/albinjm give ~1 per 2-3 y (0.085-0.127 per 100k blocks) for T5 stubborn at alpha 1/3, gamma 0.5, depth 10+; our tight model reports ~1 per 77 y for 11+ at 0.33 (git log 32f78070), i.e. ~20x rarer even though ours is an optimal attacker. Candidate causes to check, none established: depth 10 vs 11, gamma 0.5 vs 0, 80 s vs 120 s clock, tip-share counting, objective vs time normalisation. Reproduce his appendix script with MIN_REORG_DEPTH=11 before claiming a disagreement.

## 2. MRL #144 "Selfish mining mitigations (Publish or Perish)" (tevador; opened 2025-08-27, 37 comments; CLOSED 2026-11-12 with "Closed in favor of #146")
URL: https://github.com/monero-project/research-lab/issues/144. Body not edited after 2025-08-27 as far as the API shows (no dated revision).

### PoP-for-Monero soft-fork rule (quoted, body)
- "It works when the attacker's chain is less than `k` blocks longer than the honest chain (otherwise it falls back to the longest chain rule ...). A chain weight rule is applied that takes into account the block's relative time of arrival and its embedded uncle block."
- "A block is late if it arrives more than `D` seconds after any other block of the same height. This only requires relative time measurement ... Late blocks do not contribute to the weight of its chain."
- "In case of two competing chains of equal weight, the PoP paper calls for a random selection ..., but I would suggest to use a deterministic tie breaking rule (e.g. with hashing)."
- Uncle: "a new tx_extra tag for uncle blocks and each miner could include an uncle block of height exactly N-1 ... in the coinbase transaction. The uncle block is represented by its PoW header ... validate the height by checking that the `prev_id` field is the same as the one in block N-1 of the canonical chain. The approximate size ... 80 bytes ... Uncle blocks do not affect block rewards or the cumulative difficulty."
- "We would use `k = 3` ... propagation delay of `D = 5` seconds." Quoted benefit: "With `α = 0.48`, the attacker gets ~64% of the block rewards compared to ~88% with no mitigations (numbers from [5])."
### Hard-fork variant (PoP + reward splitting; never simulated: "pending Monte Carlo simulations")
Block time 60 s; lock 20 blocks; reward and penalty-free size halved; coinbase maturity 1440; block N pays the reward of N-20; coinbase carries `miner_address`; uncles (PoW header + coinbase + proof, height >= N-20) in `uncle_blocks`; PoP rule k=3, D=5 with only height N-1 uncles in weight; DAA over past 1440 blocks from N-30, trimming 120 high/low, uncles counted; reward of block N split equally between its miner and all miners of height-N uncles included in N+1..N+20. Claim: removes selfish-mining incentive "unless the attacker can mine at least 20 blocks faster than the honest majority". Comment (ArticMine 2025-09-12/15/17): fee/penalty carve-out concern; tevador: "giving 10% ... directly to the block miner might incentivize selfish mining".
### Clarifications in comments (tevador)
- 2025-08-30: if both blocks are in time "you will apply the deterministic selection rule ... you will include BA1 as an uncle block"; all valid uncles relayed; late blocks weigh 0 regardless of uncles; with D = 2x max propagation time honest blocks are always in time; under PoP "mostly 1-block reorgs and 2-block reorgs would only have 50% chance"; 3+ block reorgs need the selfish chain 3 blocks longer. Only SSH case (2 vs 1) wins unconditionally.
- venture-life 2025-09-24: simulator https://github.com/venture-life/mining-simulator (soft fork only, 2-min blocks), branch weight differences usually +-2.
- albinjm 2026-10-01 (event simulator, D=5 s, k=3, "Monero-mode rules (one uncle at N-1, ties by hash)"; exact MDP following Zhang & Preneel with author's code): optimal attacker profits from alpha 0.264 under PoP (also with hash ties and truncation 20); Nakamoto optimum gamma 0 from 0.329 (0.304 at their measured gamma); at alpha 0.33 optimum 0.362 PoP vs 0.331 Nakamoto. Conservative release at lead 3 (Qubic pattern) breaks even at 0.262 (PoP) vs 0.357 (longest chain) at zero delay; 0.296 vs 0.317 at 3 s; pays for alpha ~0.30-0.43 (+3.6 pt at 0.40). SV-release at 0.33: 270-274 10+ reorgs per 100k blocks under PoP vs 78-100 Nakamoto; zero-hash delay adversary 22.7 per 100k (PoP) vs none. Deep-branch contests 115.2 vs 23.5 (selfish) and 60.7 vs 9.8 (conservative) per 100k. Ren Zhang (2026-09-28, quoted): "I would not recommend a faithful implementation of this design"; concern about blocks published "on the verge" splitting honest power; his MDP README lists that strategy as uncovered.
### Relevance to pcmdp
- The Monero variant differs from Zhang & Preneel's model in four ways our PoP port must carry: (a) one uncle, height N-1 only; (b) deterministic hash tie-break instead of random 0.5 (pcmdp `tie` argument exists; hash tie-break = effectively per-block coin, check it equals 0.5 in the MDP state); (c) uncles do not change cumulative difficulty or rewards (soft fork); (d) D=5 s, k=3. albinjm's check suggests (b) does not move the 0.264 threshold; ours reproduces 0.2640.
- #144 is closed: the PoP-Monero MDP is a comparison baseline, not a live proposal. The hard-fork reward-splitting variant has no simulation anywhere; ours would be the first (needs 60 s blocks, 20-block splitting window, 1440 maturity).
- Missing from our PoP port (the gap Ren Zhang flags): the "on the verge" in-time/late split-view attack. It is outside Zhang & Preneel's MDP too; it needs a lateness-view state like SoP's.

## 4. Rucknium (2025-09-26), "Monero's 18-block reorg ..."
URL: https://rucknium.me/posts/monero-18-block-reorg/ (20 min read; text cached ruc/p.txt). Lock of 10 blocks protects below 10; FCMP: every transaction above the lock would be invalidated (not ~half), and the ring-elimination privacy leak disappears.
Relevance: justifies the disruption objective (reorg > 10 blocks) and depth histogram; sets the depth where harm starts (>= 10 orphaned blocks above the lock: with 18 blocks, 8 had invalidations). Suggest adding an "invalidation-weighted" output (harm per reorg block: ~0 below depth 11-12, ~100% under FCMP above the lock).

## 5. Lee & Kim, "Inside Qubic's Selfish Mining Campaign on Monero" (arXiv 2512.01437)
v1 2025-12-01, v2 2026-02-01, v3 2026-07-18, v4 2026-07-30, v5 2026-08-01 (AFT 2026, London, Oct 6-9). Data/code: https://github.com/shlee-lab/Qubic-selfish-mining-study (not fetched). I read v5 HTML and the v1/v2 abstracts only (v3, v4 not compared). v1/v2 abstracts: ten intervals, hashrate share "23-34%", conservative-release model; v2 adds intermittent mining argument (profit by intermittency under Monero's sliding-window DAA). v5 abstract drops the intermittent-profit claim: "Across the campaign, it gained no reward advantage over honest mining."
Empirical numbers (v5):
- Observation: node 2025-09-29 to 10-17; pool job feed (5 s polls) 2025-09-26 to 10-17; campaign began Aug 2025 (earliest view-key epoch 2025-08-06). Union 58,944 blocks, 13,782 attributed to Qubic; 13,771 in community set; 99.92% (12,989/13,000) heuristic confirmation.
- Share alpha = Qubic blocks / all (main + orphan) blocks: mean 23.38% over the window; 28.33% across ten sustained-activity periods P1-P10 (alpha by period 0.318-0.383 in Table F, e.g. P1 0.3532, P2 0.3831, P3 0.3378, P4 0.3370, P5 0.3182, P6 0.3223, P7 0.3264); P8 26.05% (most intensive, 1,700 accepted blocks); hourly share briefly >50%, daily and weekly never reach 51%. Qubic press release (2025-06-09): hashrate rose from <2% to >10% since 2025-05-18.
- Orphans: outside campaign "almost exclusively length one"; during it longer chains and multi-block forks (histogram only in figures; no max depth stated besides Rucknium's 18). Period detection thresholds tau_min = 2 orphans/hour, d_min = 4 h, g_max = 6 h.
- Tactics: release mostly at lead 1 in P1, P3, P4 (standard Eyal-Sirer); "release at lead 2" patterns dominate in P8; conservative strategy modelled as Eyal-Sirer except at private lead 3, where an honest block triggers full publication of 3 blocks and return to state 0. Self-forks (two Qubic blocks, same parent): 11 verified, 9 between Aug 14-17 (job coordination failure; P2 six self-forks in ~95 min).
- gamma: weekly tie-break estimate "close to zero" (Qubic blocks arrive after competing blocks despite earlier timestamps; mean delay between block timestamp and next job fetch 5.61 s, 86.3% within 8 s). Race wins above alpha in 8 of 10 periods (P1 0.49 vs alpha 0.35, P3 0.60 vs 0.34, P7 0.40 vs 0.33; P2 0/14).
- Revenue: at alpha 28.33%, gamma ~ 0: standard model 24.56%, conservative 23.71%; observed P1-P10 main-chain share 25.75% (29.88% vs alpha 31.53% without P8); target-rate share 25.11% (3.22 pt shortfall). P1, P3 beat honest. Across P1-P10 plus gaps, 11,045 accepted blocks vs 11,505.0 honest expectation = -4.0%; DAA spillover +461.8 block-equivalents (+6.3%) in gaps. Fees < 3% of rewards.
- Countermeasures and community: encrypted solution messages (XOR first, then rotating keys), withheld transactions from templates so blocks could not be reconstructed in advance; community reconstructed and relayed blocks.
- Mitigation discussion: freshness-aware rules (PoP style) "effectiveness depends on assumptions about timing and propagation"; detective mining as an alternative.
Relevance to pcmdp: validates alpha range 0.25-0.38 as the real regime (not 0.45), gamma ~ 0 (our Nakamoto gamma-0 baseline and the low-gamma grid are the observed regime), partial strategy = Eyal-Sirer plus a "release at lead 3 / lead 2" policy that pcmdp can score exactly (compare the optimal policy to the conservative one in SoP and PoP). They found no profit, consistent with the optimum at gamma 0 only exceeding alpha above 0.329 under Nakamoto: reproduce their Table F points against SSZ values at gamma 0 (alpha 0.2833: honest 0.2833, SM 0.2456). Disruption, not profit, is the observed outcome, which supports our disruption objective.
