## 2. Protocols and models
Common (paper III-B/C): one attacker, alpha < 0.5, zero natural orphan rate, no fees, no difficulty adjustment, at most two chains (public + attacker). Step = publish, reward-settle, mine one block (Fruitchains/Subchains: one unit). Attacker utility depends on the metric (section 3). gamma = share of honest power mining on the attacker chain in a tie. Illegal actions: transition to base state with Rh = 10000 (every InitStates.m, e.g. `Chain Quality/PublishOrPerish/InitStates.m:38`). Invalid or truncated states favour honest miners ("favor the compliant miners").

## 3. Metrics
All attack metrics are MDP long-run ratios or average rewards; solver = MDPtoolbox `mdp_relative_value_iteration` (RVI), tolerance epsilon/8 with epsilon = 1e-4 unless noted.
1. Chain quality Q(alpha) = min_s lim Bc/(Ba+Bc) with orphans paid 0, so Q = 1 - attacker relative revenue. Code: bisection on rou in [0,1] on W = (1-rou)Rs - rou Rh, test RVI gain > 0 (`Chain Quality/Bitcoin/SolveMDP.m:8-21`, stop at epsilon/8); result rou = LOWER bound on attacker revenue (`:24`). Second bisection (`:27-60`) over-pays at the cap (states a == lmax or h == lmax get the closed-form adopt reward `:35,41-43`), bracket [rou, min(rou+0.1,1)], gives the UPPER bound (`:62`). Both are kept only for NC/UTB/UDTB (UDTB epsilon 1e-5 at `UDTieBreaking/SolveMDP.m:6`; UTB 1e-4). SHTB (`SmallestHashTieBreaking/SolveMDP.m`): epsilon 8e-4 (line 4, "lower precision for faster convergence"), bracket starts at 0.99 alpha to alpha/(1-alpha), returns lowRou, upper-bound loop commented out. PoP: single bisection on [alpha, alpha/(1-alpha)], returns last midpoint `rou` (`PublishOrPerish/SolveMDP.m:10-28`); no upper bound.
2. Profitable threshold PT (Table II) = largest alpha with Q = 1 - alpha, by bisection on alpha: PoP `Threshold.m:10-25` (bracket [0.25, 0.275], maxB 20, "profitable" iff rou >= alpha + 1e-4, stop width 5e-5); SHTB `Threshold.m:13-28` (bracket [0, 0.1], lmax 40, test `lowerBoundReward > alpha`, no margin); UDTB `Threshold.m:9-24` (bracket [0.22, 0.25], lmax 80, test >= alpha+1e-4); RS `Incentive Compatibility/RewardSplitting/Threshold.m:11-49` (To 9, gamma 0, bracket [0.3702, 0.3787], extra downward 1e-4 walk `:40-47`, margins 1e-4 / 2e-5 / 2.5e-5). No script for UTB, NC (closed forms 1/3, 1/4, 0), or Table IV's other PT cells.
3. Incentive compatibility I(alpha) = 1 - (attacker reward share), rewards per protocol (Table III-V). Same bisection as 1; for Fruitchains/RS/Subchains only the lower-bound bisection (upper bound commented out), so reported I = 1 - rou is an UPPER bound on I as the paper says (Tables III, V captions "computed as upper bounds"). IC NC SolveMDP.m is byte-identical to CQ NC.
4. Subversion gain S = max_s lim (sum Ra + sum Rds)/t - alpha. Code: no ratio, plain RVI on Rs with Rds folded into the reward (`Subversion Gain/BitcoinDS/InitStates.m`: DSRcur = DSR*(h-cfN+1) if h >= cfN and not `matched`); `SolveMDP.m` returns RVI gain per step = (block reward + double-spend reward) per block; the "- alpha" is applied outside the code (Results.xlsx rows 3-6 vs 10-13). Fruitchains: reward x (1+bfRatio) (`FruitchainsDS/SolveMDP.m`); Subchains: reward x mtimes. Paper says "lower bound" for Subchains and Fruitchains only (action set restrictions).
5. Subversion bounty Rsb(alpha, sigma, gamma 0.95) = least Rds at which the optimal policy at the start state `baseStateS` is override (not adopt/wait). Bisection to 5e-5 on DSR in [0, 800] (NC, `BitcoinDS/SubversionBounty.m`, lmax 80/160) or doubling then bisection from 10 (RS, `RewardSplittingDS/SubversionBounty.m`, lmax 30, To = sigma).
6. Censorship susceptibility C = max lim Oc/(Oc+Rc) (Oc = honest loss). Code: same ratio bisection as 1 with Rs = honest losses (`Censorship Susceptibility/Bitcoin/InitStates.m` override Rs = h, not h+1). NC runs the revenue-style upper-bound routine too (`Censorship Susceptibility/Bitcoin/SolveMDP.m:27-62`, which uses the REVENUE closed-form cap reward); the others return rou only.

## 5. Code vs paper (discrepancies and undocumented choices)
1. PoP PT: paper 0.2500; the shipped Threshold.m (bracket lower end 0.25, `:10`) cannot return below 0.25 and returns 0.2642 (Review: (0.26421, 0.26426], maxB 20); the exact optimum gives honest = optimal until 0.26403. 0.25 is the last grid point with ideal Q (xlsx row 19), not computed. Fig 2 PoP alpha 0.30 = 0.016 is consistent with 0.264.
2. SHTB PT: paper 0.0652; exact threshold 0.05801 (lmax 10, 20 agree; 15 regions). The shipped script (`Threshold.m:21`, tolerance 8e-4 in SolveMDP) lands at 0.0653-0.0654 (Octave); gap is bisection/RVI noise, not model difference. PT ~ 1/regions (10 regions 0.0818, 5 regions 0.1387).
3. PoP maxB: Init.m 28, Init30.m 30 (paper 30), Threshold.m 20; text says convergence checked by dropping lmax 2. Init.m default alphas [0.4 0.35 0.3] only, so the paper's full 0.1-0.45 Fig 2 PoP row is not what Init.m runs; 0.45 not converged (dropped).
4. NC lmax: paper says 160 for NC/UTB/UDTB, code uses 80 for alpha <= 0.4 (CQ Init.m:17-21 and UTB, UDTB). Paper: bounds differ <4e-5; Init.m comment says even 160 not always enough at high alpha.
5. UDTB/UTB Init defaults: UDTB alphaGroup = [0.45] only, gamma loop absent; UTB gamma 0.5 only. UTB for gamma 0 and 1 not scripted (paper Table II lists UTB only without gamma; Fig 2 has one UTB curve = gamma 0.5).
6. SHTB hash regions: Init.m range = 15 and paper text 15; Appendix A describes 10 regions in the encoding and example (`hash in [0.1h, 0.1(h+1))`, probability 3/10). Appendix wording only.
7. SHTB epsilon 8e-4 (`SolveMDP.m`), lowerBoundReward = lowRou (not the last midpoint as in PoP and others), upper bound commented out: Table II/Fig 2 labelled "upper bounds" on Q / PT (consistent) but not computed with the same stopping rule as NC.
8. PoP tie is hard-wired 0.5 (honest on attacker branch in a match); "gamma" in Fig 2 for PoP has no knob. PoP's match branch uses `honestLuck` without setting it on the "publish everything" path (`InitStates.m:180`; PCMDP/pop.py notes it carries a stale value from a previous state). State numbering lets Dw overflow into neighbouring digits for out-of-range values (pop.py docstring).
9. Fruitchains IC Init1 uses lmax 28 / To 7, paper says lmax 20 for all Fruitchains IC; Init2-4 use 20. Init1 omits alpha 0.1 (Table III states I(0.1) = 0.9).
10. Subchains IC Init.m runs gamma 0.5 and 1 only and Ratio_w2b 2 only; Table V needs gamma 0 and Ratio 3 (edit mtimes, add loop). Not in repo.
11. RS IC: Init1-3 provide To = 3, 6, 9 with different alpha sets; Table IV PT is scripted for (9,0) only. PT for the other eight rows has no script.
12. SG Fruitchains lower bound claim and "Fruitchains appears better at alpha 0.45 due to limited action set": code enforces override-all only (no partial publication) as stated.
13. CS NC `SolveMDP.m:27-62` applies the revenue over-paying cap formula (`mid1`, `mid3`) to a censorship reward whose Rs = h; the resulting `upperBoundReward` is not a valid bound for that objective, and the paper reports no NC CS bounds. Which of lower/upper the xlsx NC CS row is: not stated (likely lower; unverified).
14. Aumayr's copy of NC SolveMDP drops the separate lower/upper storage and returns the upper-bound bisection capped at lower + 0.1 (Review Q1): their Bitcoin baseline at alpha 0.44-0.45 is lower+0.1; true gamma 0.5 optimum 0.5725 (alpha 0.40), 0.7596 (0.45).
15. Paper III-A: "S = ... - alpha"; the code returns the un-subtracted average; Results.xlsx has both. SG per-step rewards are per block interval for NC/RS, per block after x(1+bfRatio) for Fruitchains, after x mtimes for Subchains.
16. Fig 2 caption: alpha 0.45 (PoP) and alpha >= 0.4 (SHTB) "do not converge": the code has no convergence test; it was done by hand by lowering lmax by 2.
17. Paper says MDP exact only below ~10^7 states, PoP maxB>12 "becomes slow" (Init.m comment) yet 28-30 used.
18. Fig 6 caption says Rds = 3 where text variable is Vds = 3 (notation only).

## 7. What should change in how we run or compare
